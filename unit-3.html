01 • WEB SERVICES

Introduction to Web Services

A web service is a software component that allows one application to communicate with another application over a network using defined interfaces and message formats. It commonly uses web technologies and standard protocols.

Example

A travel website may request flight information from an airline's system. The travel website sends a request, the airline service processes it, and the result is returned to the website.

Characteristics

  • Interoperability: applications built using different languages or platforms can communicate.
  • Loose coupling: the client and service depend on a defined interface rather than each other's internal implementation.
  • Reusability: one service can be used by multiple applications.
  • Network accessible: services are available through network endpoints.
  • Machine-to-machine communication: data is exchanged using structured messages.

Common web service styles

SOAP-based REST-style
Uses SOAP messages, often XML, and a formal service contract such as WSDL. Uses resource-oriented URLs and standard HTTP methods.
Protocol with defined message structure and processing rules. Architectural style; commonly uses JSON, but can use other representations.
Often used where formal contracts and enterprise messaging features are required. Common for web and mobile APIs.
02 • ARCHITECTURE

Web Service Architecture

A traditional web-services architecture has three important roles: service provider, service requester (client), and service registry. The provider creates and publishes the service; the requester finds and uses it; the registry stores service descriptions for discovery.

Service Provider — publish —> Service Registry
Service Requester — find —> Service Registry
Service Requester — bind / invoke —> Service Provider

Three basic operations

  1. Publish: provider publishes service information or its description.
  2. Find: requester searches for a suitable service.
  3. Bind / Invoke: requester uses the service endpoint and sends a request.
Remember the roles: Provider offers the service, Registry helps discover it, and Requester consumes it.
03 • SOAP

SOAP – Simple Object Access Protocol

SOAP is a messaging protocol used for exchanging structured information between applications. SOAP messages are commonly represented in XML and are often transported over HTTP, although other underlying protocols can be used.

Structure of a SOAP message

  • Envelope: the root element that identifies the message as a SOAP message.
  • Header: optional information such as authentication, routing or transaction details.
  • Body: contains the main request or response data.
  • Fault: carries error information when processing fails; it appears within the body.
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope" > <soap:Header > <!-- Optional metadata --> </soap:Header > <soap:Body > <GetStudent > <studentId >101 </studentId > </GetStudent > </soap:Body > </soap:Envelope >

Advantages

  • Standardized XML message structure.
  • Can work across different platforms and programming languages.
  • Supports extensible headers and formal contracts.
  • Can be used with enterprise security and reliability standards.
04 • WSDL

WSDL – Web Services Description Language

WSDL is an XML-based language used to describe a web service. It tells a client what operations the service provides, what messages are exchanged, which protocol or binding is used, and where the service endpoint is located.

Common WSDL 1.1 elements

Element Meaning
types Defines data types used in messages, commonly using XML Schema.
message Describes the data exchanged.
portType Defines the abstract operations offered by the service.
binding Specifies protocol and message-format details for an interface.
service Groups endpoints through which the service is available.
port Associates a binding with a network address (endpoint).
Easy memory: WSDL is like an instruction manual or contract that explains how a client can use a web service.
05 • SERVICE DISCOVERY

UDDI – Universal Description, Discovery and Integration

UDDI is a specification for publishing and discovering information about web services. It defines a way to organize service-provider information and technical service descriptions in a registry.

Information commonly represented in UDDI

  • White pages: basic business or provider contact information.
  • Yellow pages: business categories and classifications.
  • Green pages: technical information about services and how to access them.

How UDDI fits with SOAP and WSDL

Provider publishes service description → UDDI Registry
Client discovers service → Reads WSDL → Invokes using SOAP

UDDI helps locate a service, WSDL describes how to use it, and SOAP carries the structured messages in a SOAP-based service interaction.

06 • DEVELOPMENT & DEPLOYMENT

Developing and Deploying Web Services

Developing a web service means designing its operations, implementing the service logic, exposing an endpoint, and making it available for client applications. Deployment means installing and configuring it in a server or hosting environment so clients can access it.

Typical development steps

  1. Identify requirements: decide what problem the service will solve.
  2. Design the interface: define operations, inputs, outputs and error responses.
  3. Choose technology: select a framework, language and communication style (for example, SOAP or REST).
  4. Implement service logic: write the code that performs the required work.
  5. Describe the service: for SOAP services, prepare or generate a WSDL contract.
  6. Test: test valid requests, invalid inputs, errors, security and performance.
  7. Deploy: publish the service to a web/application server or cloud platform.
  8. Monitor and maintain: check logs, availability, security and version changes.

Simple request-response example

Client application → Request → Web service endpoint → Business logic / database
Client application ← Response ← Web service endpoint

Deployment considerations

  • Server configuration and endpoint URL.
  • HTTPS and authentication where required.
  • Access permissions and input validation.
  • Database connectivity and configuration management.
  • Logging, monitoring, backups and scalability.
07 • AJAX

AJAX – Asynchronous JavaScript and XML

AJAX is a web development technique that allows a browser to communicate with a server asynchronously and update part of a web page without reloading the entire page. Despite its name, AJAX can exchange JSON, text or other data formats; it is not limited to XML.

Technologies involved

  • HTML and CSS for page structure and presentation.
  • JavaScript to send requests and process responses.
  • DOM to update page elements.
  • XMLHttpRequest or the Fetch API for network communication.
  • A server-side application to process requests and return data.

How AJAX works

User action → JavaScript request → Server processes → Response returned → DOM updated

Example: when a user types in a search box, the page can request matching suggestions from the server and show them without refreshing the whole page.

08 • PERFORMANCE

Improving Web Page Performance Using AJAX

AJAX can improve perceived responsiveness because only the required data or section needs to be updated instead of reloading the complete page. It does not automatically make every website faster; implementation and server performance still matter.

Ways AJAX can help

  • Partial page updates: update only the relevant part of the page.
  • Asynchronous requests: users can continue interacting while a request is in progress.
  • Smaller data transfer: request only the data needed for the current action.
  • On-demand loading: fetch content when it is needed rather than loading everything initially.
  • Reduced full-page rendering: avoid rebuilding the entire page for small updates.

Good practices

  • Show a loading indicator for longer requests.
  • Handle network errors and timeouts.
  • Debounce frequent events such as typing in a search box.
  • Cache suitable responses where appropriate.
  • Keep responses small and avoid unnecessary requests.
  • Use HTTPS and validate data on the server.
AJAX does not remove the need for server-side validation or security. Never trust data just because it came from your own web page.
09 • AJAX PROGRAMMING

Programming in AJAX

A typical AJAX program performs four tasks: create a request, send it to the server, receive the response, and update the web page.

Example using Fetch API

This modern example requests JSON data from an endpoint and displays a result.

<p id="result" >Click to load information.</p > <button id="loadBtn" >Load Data </button > <script > document.getElementById("loadBtn").addEventListener("click", async () => { const output = document.getElementById("result"); output.textContent = "Loading..."; try { const response = await fetch("/api/student/101"); if (!response.ok) { throw new Error("Request failed: " + response.status); } const student = await response.json(); output.textContent = student.name + " - " + student.course; } catch (error) { output.textContent = "Unable to load data."; console.error(error); } }); </script >

Traditional XMLHttpRequest example

const xhr = new XMLHttpRequest(); xhr.open("GET", "/api/message", true); xhr.onload = function () { if (xhr.status === 200) { document.getElementById("result").textContent = xhr.responseText; } }; xhr.onerror = function () { document.getElementById("result").textContent = "Network error"; }; xhr.send();

Important XMLHttpRequest methods and properties

Method / Property Purpose
open() Initializes the request method, URL and async setting.
send() Sends the request.
onload Runs when the request completes successfully at the network level.
onerror Handles network-level errors.
status Provides the HTTP status code.
responseText Provides the response as text.
responseXML Provides an XML document response when available and parsed.
Fetch is the modern, promise-based approach. XMLHttpRequest is still important to understand because it is commonly included in AJAX syllabi and older examples.
10 • DISTRIBUTED SYSTEMS

CORBA – Common Object Request Broker Architecture

CORBA is a standard architecture developed by the Object Management Group (OMG). It allows software objects in different programs, languages or machines to communicate with one another through an Object Request Broker (ORB).

Main components

  • Object Request Broker (ORB): acts as a communication intermediary. It locates the target object and helps send requests and return results.
  • Client: requests an operation on a remote object.
  • Object implementation / server: contains the code that performs the requested operation.
  • IDL (Interface Definition Language): defines the operations and data types offered by an object independently of a programming language.
  • Stub: client-side proxy code that prepares and sends a request.
  • Skeleton / servant-side mapping: server-side support that receives the request and dispatches it to the object implementation.

How CORBA works

Client → Stub → ORB → Server object
Client receives result ← ORB returns response

Advantages

  • Supports communication across programming languages and platforms.
  • Provides location transparency through the ORB.
  • Supports distributed object-oriented applications.
  • Uses IDL to define language-independent interfaces.

CORBA and Web Services

CORBA Web Services
Distributed-object architecture. Application communication using web protocols and service interfaces.
Uses ORB and IDL. May use SOAP/WSDL or REST-style APIs.
Often uses object-oriented remote invocation. Often exchanges messages or resource representations.
Designed for language/platform interoperability in distributed systems. Designed for interoperable network services, commonly over web infrastructure.
